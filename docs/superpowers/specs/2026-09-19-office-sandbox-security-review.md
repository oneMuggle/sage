## 1. 为什么现在推进（动机回顾）

对标表（docs/technical/54）最后一个 ✅ 级缺口。竞品（Claude skills /
ChatGPT code interpreter 等）用代码沙箱承接**长尾文档操作**：复杂图表、
SmartArt、条件格式细分、跨对象批量操作。Sage 目前的替代路径是逐 op
扩 `edit.py`——ops 枚举已在膨胀（round 2-15 持续加 op），每个长尾需求
都要走"设计 op → 实现 → diff 预览适配 → 测试"全流程，边际成本不降。

沙箱把长尾操作变成"模型写 python-docx/openpyxl 脚本 → 沙箱内对副本
执行 → diff 预览 → 用户确认应用"，复用已有的 diff_preview / snapshot
/ 应用确认机制，**不再逐 op 扩面**。

## 3. 威胁模型核对清单（逐项签字）

**T1 文件系统逃逸**
- [ ] 脚本仅见沙箱工作目录（源文件副本），经 `resolve_within` 同源围栏
- [ ] 路径 API 拦截：`open`/`pathlib` 经 audit hook（`sys.addaudithook`）拒绝目录外访问
- [ ] 产物回传走结构化通道（保存的副本文件），不信任脚本自报路径

**T2 网络外发（"数据不出机"红线）**
- [ ] `socket` 模块不在白名单；audit hook 拦 `socket.*` 事件双保险
- [ ] `urllib`/`http`/`requests` 均不在白名单

**T3 资源耗尽**
- [ ] 子进程 wall-clock 超时（对齐 export_pdf 的 120s 口径）
- [ ] 输出文件大小上限（对齐 read 端点 50MB 口径）
- [ ] Windows：job object 内存上限为阶段二增强项，阶段一靠超时兜底

**T4 提示注入 → 恶意脚本**
- [ ] 脚本全文在确认弹窗可见（折叠展示，默认展开 import 段）
- [ ] diff 预览是唯一生效路径 —— 即使脚本恶意，落盘仍需用户确认
- [ ] 高危 pattern 静态扫描（`eval`/`exec`/`__import__`/编码绕过）复用
  word_template 的 dangerous-Jinja 扫描思路

**T5 沙箱产物二次注入**
- [ ] 产物经现有 read_* 结构化读取渲染（P3 统一预览），不直接渲染脚本输出

## 4. 分阶段启用路径

- **阶段一（评审通过即可做）**：`office_script_preview` 工具 —— 副本上执行
  白名单脚本，返回 DiffPreviewResult。默认 **关**（设置页 opt-in +
  「实验性」标注）。win7 通道**不回流**（3.8 audit hook 行为差异待验证）。
- **阶段二**：确认应用管线（snapshot → 原子替换 → 行刷新，全部复用现有
  机制）；Windows job object 资源上限。
- **阶段三**：对标表状态翻 ✅；评估内置技能脚本库（常用长尾操作模板化）。

# 资源卫生 R29：抓取客户端泄漏 + 事件通道替换滞留（2026-09-24）

- **上游文档**：Round 27（AB3/静态抓取链）；Round 23（事件通道）
- **范围**：后端 only（web_tool.py / browser_events.py + 测试）

## 0. 结论速览

两处资源生命周期缺口（R27/R23 的代码审查中发现）：

1. **`_get_with_redirects` 客户端泄漏**：循环内重建的 `httpx.Client` 只在
   "verify 变化重建"时 close；`redirect_limit_exceeded` /
   `response_exceeds_limit` / 策略校验失败等异常路径直接抛出，client
   连同连接池一起滞留到 GC——高频抓取 + 反爬站点（常见 3xx 超限）下
   句柄稳定泄漏。修复：循环包 `try/finally client.close()`。
2. **事件通道替换滞留**：`start_event_channel` / `start_download_tracking`
   发现 `tracker.connected=False` 的旧通道时直接新建并覆盖 `_channels`
   映射——旧 `_EventChannel` 的 `stop()` 未调用，若 socket 处于半开态，
   `_loop` 读线程可无限期滞留（每轮泄漏一个守护线程 + fd）。
   修复：替换前先 `existing.stop()`。

## 设计

1. `_get_with_redirects`：client 首次创建后包 `try/finally`，
   `finally` 中 `client.close()`（成功路径 client 已在返回前缓冲完响应，
   关闭无副作用）；重建分支维持现状（先 close 旧的）；
2. 通道替换：`start_event_channel` / `start_download_tracking` 的
   `existing is not None and not connected` 分支先 `existing.stop()` 再新建；
3. 测试：
   - 假 client 记录 close 调用——重定向超限异常路径 close 恰好一次；
   - 断连通道替换——旧通道 `stop` 被调用（以 `_EventChannel.stop` 打桩）。

## 一、结论先行

**Sage 当前最值得做的，不是继续增加一级功能，而是让已有能力变得可发现、可理解、可信任、可交付。**

建议把默认产品承诺统一为：

> **本地优先、记忆增强、能按要求交稿的 AI 工作台。**

这里按 `README.md` 当前强调的 Office 写作代理定位评审；如果实际核心用户是开发者，应通过用户研究调整默认工作模式，而不是直接移除编码能力。

优先顺序：

1. **修正确性与信任问题**：项目资料实际进入上下文；关键设置保存得到真实回执；本地无密钥端点的状态一致；明确临时聊天的隐私契约。
2. **收敛入口**：首页围绕具体成果，项目成为工作容器，设置按用户心智组织，高级能力保持可发现但不抢主流程。
3. **打通交付**：需求 → 资料 → 计划/大纲 → 生成 → 预览/修订 → 校验 → 验收/导出 → 版本与复用。
4. **显性呈现可信度**：说明用了什么上下文、哪些资料未使用、操作影响什么范围、哪些检查已完成、哪些仍未验证。
5. **再做高级增长**：任务复用、按能力选模型、任务级预算、平台差异化，而不是先建设新的“功能大全”。

### 优先级速览

| 优先级 | 建议 | 为什么现在做 | 工作量判断 |
|---|---|---|---|
| P0 | 修通项目资料 `pending_index → ready → 上下文` | 否则项目记忆的核心承诺无法兑现 | 小；已有修复提交可核对复用 |
| P0 | 关键设置采用严格保存回执与失败恢复 | 避免界面显示已生效，后端实际未保存 | 小到中 |
| P0 | 统一端点协议、密钥要求和连接状态判定 | 首启与侧栏对 Ollama 的判断不一致 | 小到中 |
| P0 | 明确临时聊天、记忆、历史和云端传输的边界 | 隐私语义不宜由用户自行猜测 | 文案小；持久策略中 |
| P1 | 以成果为导向的首页与首个成功任务 | 缩短从安装到价值感知的路径 | 中 |
| P1 | 项目工作台与项目内新任务入口 | 把侧栏中的复杂管理搬到合适的空间 | 中 |
| P1 | 设置收敛、正确默认落点、搜索定位高亮 | 已有治理基础，但新旧入口仍并存 | 小到中 |
| P1 | Office 任务简报与统一交付体验 | 利用现有模板、预览、校验、版本能力 | 中 |
| P1 | 上下文/来源检查器 | 让“AI 用了什么”可以核对和纠正 | 中 |
| P1 | 任务状态与完成反馈精确呈现 | 区分运行、待授权、待验收和已完成 | 小到中 |
| P1 | 组合布局、字号与可访问性验收 | 长时间工作与窄窗口比视觉装饰更重要 | 小到中 |
| P2 | 已验收流程复用、模型能力路由与任务预算 | 在主流程稳定后提升持续使用价值 | 中到大 |

“工作量”是范围判断，不是工期承诺；实施前应核对当前分支、在途 worktree 与现有计划。

## 五、P0：先让用户看到的状态与实际行为一致

### L1. 项目资料要真正可用，而不是永久“待索引”

**源码确认，当前快照中的阻断项。**

链路证据：

1. `backend/data/project_material_repo.py:117–133` 添加资料时固定写入 `pending_index` 并直接返回。
2. `backend/api/project_routes.py:445–458,508–516` 的添加资料/保存回答入口没有将该条资料转成 `ready`。
3. `backend/data/project_material_repo.py:199–212` 供上下文读取的方法只返回 `ready`。
4. `backend/api/legacy_routes.py:1096–1102` 聊天主链路使用上述方法。
5. 对生产代码的限定搜索未发现项目资料 `mark_ready()` 的调用；出现的其他 `mark_ready` 属于编排 lane，不是资料。

因此，这条添加资料路径不能兑现“稍后可供对话使用”的承诺。不能用改徽章文案掩盖链路缺口。

**已有修复可复用：**仓库中存在提交 `4a3dd44cb`，标题为“资料添加后直接 ready，修复项目资料从不注入 system prompt”。`git merge-base --is-ancestor` 检查表明它不是本次快照的祖先。本报告未合并或检出该修复。

建议：

- 先核对并复用现有修复，不重复开一套相同实现。
- 区分“文本资料已可作为上下文使用”和“已完成向量索引”，两者不能共用一个模糊成功状态。
- 对已有 `pending_index` 数据明确修复/迁移策略，不能只让新建资料生效。
- 增加资料详情里的“可用于对话”“最近使用”“失败原因/重试”。

**验收：**添加一条文本资料 → 在所属项目发问 → 注入清单中出现该资料；另一个项目不出现；删除后未来回复不再使用；旧记录的恢复策略有覆盖测试。

### L2. 关键设置必须有严格回执

**源码确认保存失败语义存在差异；实际失败路径待故障注入。**

- `src/shared/api/settingsClient.ts:49–60,99–103` 捕获写入失败后返回 `null`，普通 `setPreference` 仍会派发设置变化事件。
- `src/pages/settings/ToolsConnectionsTab.tsx:48–53` 权限设置先更新本地显示，再调用静默写入。
- 相比之下，聊天顶栏的 `PermissionModeSwitch.tsx:102–114` 已有失败恢复与提示，可以作为统一范式。
- 首启向导 `OnboardingWizard.tsx:71–92` 发起保存后立即显示完成，未等待写入结果；是否被后续 store 机制完全补偿，需运行确认。

建议：

- 统一 `保存中 / 已保存 / 失败 / 待同步`，关键写入失败必须向调用方返回可判别结果。
- 权限、网络策略、快照、记忆、预算等不能把“本地切换完成”当作“后端已生效”。
- 缓存可维持 UI 可用，但明确显示“缓存值，尚未同步”，不能与真实生效状态混淆。
- 写入成功才派发成功事件；失败恢复上一值，并提供重试。
- 首启完成以保存与可用性检查结果为准，而不是仅完成表单。

**验收：**后端断开、超时、拒绝写入和快速连续修改时，界面不出现假成功；权限入口间一致，恢复连接后显示真实后端值。

### L3. 接入判定统一使用协议能力

**源码确认，Ollama 首启与侧栏判断不一致。**

- `Welcome.tsx:51–56` 和 `OnboardingWizard.tsx:47–58` 允许 Ollama 不填密钥，并将协议传入测试。
- `Sidebar.tsx:185–202` 仍把缺少 API Key 直接判断为未配置，测试调用也未传入协议。

建议：

- 复用同一个协议感知的“配置是否完整”和连接探测入口。
- 状态区分：未配置、配置不完整、检查中、鉴权失败、不可达、连接可用、模型不可用。
- 不把“已填 URL/Key”“列出模型”“实际支持当前任务”合成一个绿色状态。
- 若要做真实推理探测，应显示用途并限制消耗，不静默进行有费用的复杂请求。

**验收：**OpenAI 兼容、Anthropic 和无密钥 Ollama 的首启、侧栏、设置与发送失败提示一致；切换协议/模型后不显示上一个请求的过期结果。

### L4. “临时聊天”需要明确隐私契约

**源码确认现有开关语义；重启后的具体交互风险待运行验证。**

`Chat.tsx:94–113` 的临时聊天开关控制 `memory_mode='off'`，通过 `sessionStorage` 跨路由保留，应用重启会清空。后端 `legacy_routes.py:1122–1123` 将该值解释为跳过记忆注入/提取。

这不应被理解为自动满足以下所有条件：

- 不保存聊天历史；
- 不保留附件、工具日志或产物；
- 不调用云端模型；
- 重启并恢复同一会话后仍保持原隐私选择。

建议二选一，并明确显示：

1. **保留现有能力，改成“不使用长期记忆”**，写清作用范围与持续时间；或
2. **实现完整临时会话契约**，明确历史留存、附件/产物保留、服务端会话策略与恢复行为。

同时独立提供：记忆读取、记忆写入、历史留存、发送云端的资料范围。安全相关会话策略不应只依赖页面状态；恢复会话不能悄悄放宽此前承诺。

`docs/user-manual/16-project-context.md:131–137` 已明确“本地存储的资料仍可能被注入云端 LLM”。建议在用户操作处解释 **“本地存储 ≠ 本地推理”**，而不是只在手册末尾说明。

**验收：**切路由、关闭/重启、恢复历史、重新发送、模型切换都遵守界面明确承诺；不存在一次点击就让用户误以为“所有数据不出设备”的表达。

## 六、UI：减轻理解成本，不做营销式大改版

### U1. 首页以成果而非通用能力开场

**源码确认定位与默认推荐不一致；转化收益待用户测试。**

`README.md:3` 强调 Office 写作代理，`PHILOSOPHY.md` 强调第二大脑，`DESIGN.md` 描述个人知识管理工具；首页推荐却主要是写代码、搜索和脑暴（`src/entities/welcome/recommendations.ts:17–39`），轮播提示也以代码等通用任务开场（`Welcome.tsx:17–31`）。

建议：

- 统一对外定位与默认首页文案，保留 “calm, dense, operational” 的视觉原则。
- 默认四个成果任务：**写报告 / 整理资料 / 分析表格 / 制作演示**。
- 根据用户选择和已有项目类型调整推荐；开发者模式仍可展示代码任务。
- 首页带“当前项目 / 不绑定项目”选择，开始前解释文件落点与资料范围。
- 推荐卡点击后打开任务简报或填入可执行示例，不只是“帮我写代码：”这样的空前缀。
- 首次成功引导到一个小而完整的结果：选择资料 → 确认需求 → 得到可打开的文件。
- 修正 `Welcome.tsx:33,78–98` 的泛 GitHub 链接；已标不可用的 WebUI 入口不宜仍像正常快捷任务，地址也应读取实际配置而非固定端口。

首启已有三步向导，不需重做一套：优先修回执与状态，再补“第一次完成任务”的引导。

### U2. 项目成为真正的工作容器

**源码确认目前复杂项目管理仍内嵌侧栏。**

`ProjectSection.tsx:875–880` 将会话、概览和资料等面板放在项目行内部；当前 `App.tsx` 路由表未见独立项目主页。

建议：

- 侧栏负责选择项目和切换会话；项目工作台承载目标、约束、资料、会话、成果、运行中任务和设置。
- 新任务默认明确其项目归属，历史会话支持可见的归属与迁移确认。
- 复用已有项目类型、约束与里程碑组件，不重新建设项目分类系统。
- 将项目身份与文件读写工作区分别表达：项目决定上下文，目录绑定决定文件能力和权限。
- “虚拟项目/无需目录”属于后续数据模型评估，不与首轮 UI 调整强绑；不得为了便利破坏已有目录授权边界。
- 项目级成果视图复用现有产物、Office 文档与任务元数据，不建立另一份不一致的文件副本清单。

### U3. 完成设置治理的最后一公里

**源码确认：**

- `Settings.tsx:69–88` 目前仍显示 15 个 tab，更新源功能开启时更多；已经有基础、记忆与知识、工具与连接分组，但旧细分入口仍并存。
- `Settings.tsx:46–55` 无已保存值时默认 `general`，而导航列表没有此项；老容器仍能渲染，造成默认页面与导航选中状态不一致。
- 设置项搜索已有实现，但 `jumpToItem` 目前只切 tab（`Settings.tsx:98–101`），没有在该入口传递目标项的定位与高亮。

建议默认收敛为：

1. 基础与外观；
2. 模型与服务；
3. 记忆与资料；
4. 工具与安全；
5. 网络与远程；
6. 诊断、用量与更新。

旧 tab/key 保留兼容映射，但不要求普通用户同时理解新旧两套入口。预算应出现在模型/用量语境，快照应出现在安全/文件语境。搜索命中后滚动到项目、高亮并支持键盘到达，避免“搜到了但仍要在长页找”。

### U4. 按任务动态呈现聊天工作区

已有折叠侧栏、右侧 push/overlay、宽度档位和最大化能力。优化重点应是组合状态：

- 聊天头部默认只保留项目、模型和必要安全状态；用量详情、分支、上下文细节按模式或菜单展开。
- 普通用户选择“快速问答 / 资料研究 / 文档任务 / 执行任务”，不需要先理解 `force_multi` 或编排模板内部名称。
- 右侧以“成果 / 过程 / 资料”三个用户心智组织；预览是成果的查看状态，变更属于成果修订，目录是会话阅读工具。可在保留底层 tab/API 的前提下先做导航收敛。
- 保留高级快捷入口与渐进解锁，同时增加稳定的能力目录和显式显示/隐藏控制；不把“曾访问过路由”作为唯一发现机制。
- 在窄窗口中保证输入、停止、确认操作始终可达；高密度不等于将关键状态缩到 10px。

建议布局示意，非真实运行截图：

```text
┌────────────┬─────────────────────────┬──────────────────┐
│ 新任务     │ 项目身份 · 模型 · 范围  │ 成果工作区       │
│ 项目       ├─────────────────────────┤ 最新文件/版本    │
│ 会话       │ 对话与当前任务          │ 预览、选区修订   │
│ 文档       │ 计划、必要确认、结论    │ 来源与检查状态   │
│ 任务       ├─────────────────────────┤                  │
│ 资料/记忆  │ 输入 + 附件 + 任务模式  │ 按需打开         │
│ 能力/设置  │ 运行 / 待确认 / 已交付  │                  │
└────────────┴─────────────────────────┴──────────────────┘
```

### U5. 统一设计语义与可访问性验收

`tailwind.config.js:78–98` 已有变量化字号，因此不能把现有 `text-sm` 简单说成不支持缩放。但同时存在传统字号与 `text-ui-*` 两套语义，应统一角色映射，避免同名“小字”在不同区域表示不同层级。

建议：

## 七、功能：把 Office 和知识能力做成完整成果流程

### F1. 默认用“任务简报”，字段式创建保留为高级入口

Office 页面已有结构化创建和模板实例化，不应再以“从零建设文档生成”为建议。新的入口应该让用户表达：

- 给谁看、解决什么问题；
- 使用哪些资料；
- 需要多少页/字、什么语气；
- 哪些格式规范、模板和引用要求；
- 交付 Word/Excel/PPT/PDF 中的哪几种。

随后接已有写作/编排能力，而不是要求用户先手工填完文档内容字段，再回聊天里找 AI。

推荐交付流程：

```text
任务简报 → 资料范围 → 可编辑的大纲/计划 → 生成草稿
       → 预览与选区修订 → 检查清单 → 接受/打回
       → 导出/打开 → 版本保留 → 保存可复用任务
```

复用现有模板库、预览、编辑 dry-run、格式 Linter、快照和交付抽屉；各格式使用不同检查清单，不能把 Word 的检查原样套给表格和演示。

完成卡分别显示：

- **执行结果**：文件是否生成；
- **格式检查**：哪些规则通过/未通过；
- **内容与来源检查**：已核验、需人工检查或未核验；
- **交付状态**：可编辑、可打开、待验收、已接受。

**“工具调用成功”不等于“可交稿”。** 自动检查不能用一个没有依据的可信分数替代真实检查结果。

### F2. 建立上下文/来源检查器

Sage 已有记忆写入提示、项目资料、附件引用和 Wiki 来源相关实现。下一步应回答：**这一轮实际用了什么？**

发送前显示简要清单，发送后允许追溯实际使用范围：

- 当前项目及项目指令；
- 明确引用的文件/片段；
- 检索到的 Wiki/网页来源；
- 使用的长期记忆；
- 被截断、未索引、超预算或被用户排除的资料。

每项提供来源跳转、范围、使用状态和本次排除操作；用户不需要阅读完整 system prompt，也不应依赖公开模型完整推理过程。

`docs/user-manual/16-project-context.md:110–117` 已说明资料可能按预算截断/排除，但建议把重要资料“写进指令”不是理想产品替代方案。应提供“本次必读/固定引用/按需检索”与可见预算；事实资料仍是数据，不因重要就升级为高优先级行为规则。

项目资料按项目 ID 隔离已有明确设计，不能再以“新增资料隔离”为建议。需要进一步运行核对的是全局长期记忆、Wiki、文件引用与项目范围的组合行为；实现“仅本项目”控制前必须核实后端真正的筛选范围。

来源应保留类型、位置、原始链接/文件、获取时间和核验状态。AI 生成并保存的资料也需要来源标签，不应被默认视为已验证事实。

### F3. 只把已验收的工作流做成可复用任务

技能、Prompt 模板和定时任务已经存在。建议打通它们，而不是再添加一个互不关联的自动化入口：

- 从已验收成果保存“任务配方”：输入字段、资料范围、模板版本、检查标准、输出位置。
- 允许用户将配方设为一次运行或定时运行，明确权限与预算。
- 定时结果进入项目成果和现有任务中心，并通知待处理事项。
- 资料变化、权限失效、格式检查失败时阻断/请求确认，不静默生成看似完成的错误文件。
- 重试和续跑要有幂等性验收，不能因重复发送创建多个成果或重复执行外部操作。

优先选择真实高频任务，如周报、会议纪要、数据汇总；不从“支持更多自动化平台”开始。

### F4. 模型选择从型号选择升级为能力与预算选择

复用已有端点、会话模型、fallback、用量与每日预算能力：

- 默认展示“快速 / 高质量 / 本地”或任务适配方案，型号信息仍可展开。
- 路由依据应包含工具调用、视觉、长上下文、结构化输出等能力，不能只看模型名称。
- 降级不能悄悄把需要视觉/工具的任务切到不支持的模型。
- 提供任务级预算与终止条件，区分估算、已消耗、未知价格。
- 多代理仅在确有收益的任务启用，说明执行范围、额外消耗及可能等待时间。
- 使用云端模型时，清楚显示提供方及本轮会发送的资料范围。

自动路由和任务级预算属 P2，优先级低于当前配置与回执一致性修复。

## 八、逻辑：复用统一任务中心，把状态表达做准确

**已有统一状态，不建议另建一套任务状态系统。**

`TaskCenterWidget.tsx:65–84` 已映射 queued、running、awaiting_approval、paused、succeeded、failed、cancelled。建议在此基础上改善两点：

1. **授权与验收分开表达。** `TaskCenterWidget.tsx:97–104,234–242` 将执行成功但未验收的 lane 显示为 `awaiting_approval`；用户应能区分“允许执行下一步”和“检查已经生成的成果”。可先由现有 metadata 派生显示状态，不必立即更改所有后端协议。
2. **终态不持续像运行中。** 完成 registry 条目会保留，而 `busy` 以条目总数判断，胶囊一直使用旋转图标（`TaskCenterWidget.tsx:249–250,301–384`）。建议旋转仅表示实际 running，其他显示待处理/完成标记，数量分为运行、待授权、待验收、失败和完成。

进一步验收：

- 取消按钮显示“取消请求中”，后端确认后才显示取消完成；
- 网络断开显示状态未知/重连，不伪造失败或成功；
- 恢复使用后端运行 ID 与已有重接机制，不让页面加载状态重新定义任务事实；
- “重新发送最后一条消息”与“重试原任务”在可能有副作用时必须有清晰区别；
- 审批、快照、版本、任务产物与审计信息可互相回跳。

已有执行边界验证记录 `docs/verification/2026-09-27-office-execution-boundary.md` 应作为后续改 UI 的约束；不能因改善交互而绕过 staging、审批或产物归属规则。本次未重新执行该验证。

## 九、落地路线：三批滚动，不做全站重构

### 批次 A：可信底座与小成本修复

- 核对/复用项目资料修复与旧数据恢复策略。
- 关键写入严格回执、状态回滚、统一端点判定。
- 明确临时聊天的契约与恢复行为。
- 修设置默认落点、无效旧 tab 的回退、首页错误/不可用链接。
- 任务胶囊不以持续旋转表示全部终态条目。

**退出标准：**这些功能在明确的失败用例中不出现假成功；资料确实被正确范围的对话使用。

### 批次 B：一条端到端主流程

只选一个真实场景，例如“根据指定资料生成一份符合模板的中文报告”，完成：

- 成果任务首页入口；
- 项目工作台 MVP；
- 任务简报与资料范围；
- 预览/修订/检查/验收/导出一致的交付卡；
- 来源和上下文追溯；
- 新手任务测试及组合布局验收。

**退出标准：**用户不需要理解内部模块和编排术语，就能完成并找到可交付成果。不要同时改完所有场景。

### 批次 C：持续价值与差异化

- 将已验收任务保存为配方，接现有技能和定时任务。
- 模型能力路由、任务预算和明确降级。
- 按真实需求评估虚拟项目、OCR、受控文档沙箱等长尾能力。
- 主线与 Win7 LTS 保持独立体验/依赖节奏；有能力差异时明确说明并降级，不让兼容分支冻结主线所有体验。

主线依赖升级需要独立安全与兼容评估，不与产品 UI 评审捆绑实施。已有 FSD/六边形架构不应为这轮优化推倒重建。

### 实施纪律

遵守仓库 `AGENTS.md`：功能批次先有方案、独立 worktree、先确认所有权与现有改动、按范围验证、推送前核对 base、CI 为最终门禁。不因文件大而自动大重构，优先聚焦拥有该行为的组件/服务和小型辅助函数。

## 十、建议的验收指标与测试场景

以下是**待建立的指标/目标**，不是本次测得的数据。

| 指标 | 如何定义 | 用途 |
|---|---|---|
| 首个成功任务时间 | 从已有可用端点的首次进入，到打开第一份通过所需检查的成果 | 不把填 Key/下载模型时间与生成体验混为一谈 |
| 主旅程完成率 | 开始任务且成功验收/导出的比例，按场景区分 | 北极星优于消息数量 |
| 人工返工次数 | 从首稿到接受的修改轮次与修改类型 | 找到格式/资料/内容哪一环薄弱 |
| 状态真实性 | 保存、取消、失败、完成的 UI 与后端一致性 | 故障注入用例中假成功应为 0 |
| 来源可追溯率 | 明示来源能够跳转到正确位置的比例 | 用固定测试语料先保证链路，不宣称自动保证事实正确 |
| 恢复正确性 | 断网、切页、重启、重试之后不丢状态、不重复副作用 | 衡量桌面代理可靠性 |
| 已验收任务复用 | 被实际再次成功执行的任务配方比例 | 比新增技能/模板数量更有意义 |
| 成功成果成本 | 同场景、同模型/端点下的实际成本与耗时 | 评估路由和多代理收益 |

起步可提出“首个成功任务时间下降 30%”之类相对目标，但须先记录基线，并保持模型、端点、机器和任务相同；这不是目前的实测承诺。

建议至少覆盖八条旅程：

1. 无密钥 Ollama → 首启 → 正确连接状态 → 发出第一轮请求。
2. 云端鉴权失败/限流 → 有可理解原因与恢复入口，不生成假成功。
3. 设置写入超时 → 显示失败/待同步 → 重试成功 → 多入口一致。
4. 项目 A 添加资料 → A 使用 → B 不串资料 → 删除后未来不使用。
5. 关闭长期记忆/临时模式 → 切页/重启/恢复 → 仍遵守明示策略。
6. 中文报告 → 资料与格式要求 → 预览修改 → 校验 → 导出 → 历史版本恢复。
7. 后台长任务 → 切页/断网/重接 → 取消/失败重试 → 不重复产生副作用。
8. 1024×768、高 DPI、UI 大字号、深浅色、英文、纯键盘 → 关键操作始终可达。

产品指标优先本地汇总或经明确同意再上报；不收集聊天正文、资料内容、密钥和完整本机路径来做默认遥测。
